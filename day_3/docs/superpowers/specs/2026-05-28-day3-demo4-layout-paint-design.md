# Day 3, Demo 4 — "The expensive DOM" (Layout, reflow, and paint)

**Date:** 2026-05-28
**Status:** Approved design
**Part of:** Day 3 — Demystifying Frontend Engineering. Fourth demo; turns the
"render" half of the pipeline (after Demo 3's render-blocking) into a
performance story, and sets up the virtual DOM in Demo 6. Continues the Swiggy
spine.

## Purpose

Make DOM cost **visceral**, then name **why** it matters.

Changing the DOM forces the browser to recompute layout (**reflow** — where every
box sits) and **repaint** the affected pixels. One change is cheap; 500 changes
in a loop, with a layout read interleaved, is **layout thrash** — the browser
reflowing repeatedly because the code keeps asking for fresh layout between
writes. This is the concrete reason manual DOM manipulation gets slow at scale,
and the framing for the whole React arc: **"updating a complex UI efficiently is
hard when done manually"** — explicitly *not* "HTML is hard to write."

## Approach

Build **one page, 500 small restaurant tiles** in a CSS grid (emoji + tiny label,
generated by JS). Provide two buttons that reach the **same visual result** by
opposite methods, each timed with `performance.now()` and shown on screen so the
contrast is quantitative and repeatable. A Reset button rebuilds the grid.

- **"Resize each (slow)"** — loop over all 500 tiles, set
  `element.style.width/height/fontSize` per tile, and **read `offsetWidth`**
  immediately after each write. The read forces the browser to flush a
  synchronous reflow *that iteration*, so 500 writes become 500 reflows — the
  canonical layout-thrash anti-pattern.
- **"Resize all (batched / fast)"** — clear any inline sizes a prior slow run
  left, then toggle a **single class** (`.big`) on the grid container. CSS
  resizes all 500 tiles, and one trailing `grid.offsetWidth` read forces the
  **one** layout/paint to land inside the timer. Same final look, a fraction of
  the time.

Both timings render to the page (`—` until clicked). Exact ms are
machine-dependent; the **ratio** is the teaching point.

## Demo flow (lands in `README.md`)

0. **Slido** (before anything): "Update 100 list items — (A) one by one, or (B)
   rebuild the whole list as HTML and replace at once?" Hold the twist.
1. DevTools → Rendering → enable **Paint flashing**; interact with any page —
   green flashes are repaints.
2. Open the 500-tile page. With the **Performance** tab recording, click
   **"Resize each (slow)"** → point at the long Layout→Paint→Layout→Paint bars;
   note the large elapsed-ms readout. "500 individual layout recalculations."
3. Reset, then click **"Resize all (batched)"** → one Layout, one Paint, tiny
   elapsed ms; identical final look.
4. Land it: **"This is the core problem React was built to solve"** — efficient
   UI updates by hand are hard, not HTML authoring.
5. Pay off the Slido: **B** wins on speed (one pass vs 100) but loses scroll
   position, focus, and in-flight animations — the tension the **virtual DOM**
   resolves. Forward-ref to Demo 6.

## Verification

- `test_server.py` passes in a local `.venv` (index + `style.css` + `app.js`
  serve 200 with correct content-types; grid + buttons present; requests
  logged).
- The two buttons produce the **same** final tile size (slow path clears inline
  styles before the class toggle wins; fast path matches the `.big` rule).
- Performance behaviour (slow ≫ fast, repeated vs single Layout/Paint) is
  confirmed **manually** per the checklist — the automated test only checks
  serving.

## Out of scope

- A precise benchmark harness or averaging across runs (one live click per path
  is enough to land the contrast).
- `requestAnimationFrame` batching, CSS containment, or `will-change` tuning
  (mentioned conceptually at most; not built).
- The virtual DOM / diffing itself — that's Demo 6; here we only motivate it.
- Reusing Demo 1's image/font/external CSS (kept self-contained and offline:
  emoji + gradients only).
